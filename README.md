# Provenance Guard

A backend classification system that analyzes text submissions and determines whether they were likely written by a human or generated by AI. The system runs two independent detection signals, produces a confidence score, returns a plain-language transparency label, and gives creators a way to appeal if they think the result is wrong.

## Architecture Overview

When a creator submits text through `POST /submit`, the system validates the input, then runs it through two detection signals in sequence. Signal 1 (Groq LLM) evaluates the text for semantic patterns common in AI writing. Signal 2 (stylometric heuristics) measures structural statistics like sentence length variance, vocabulary diversity, and punctuation density. Both signals return a score between 0.0 and 1.0, which are combined into a single confidence score using a weighted average (60% LLM, 40% heuristics). That score maps to one of three transparency label tiers. The full result gets written to a structured audit log, and a JSON response goes back to the creator.

For appeals, a creator sends `POST /appeal` with their content_id and reasoning. The system looks up the original classification, updates the status to "under_review," logs the appeal alongside the original decision, and returns a confirmation.

The full architecture diagram is in `planning.md`.

## Detection Signals

### Signal 1: LLM-Based Classification (Groq, llama-3.3-70b-versatile)

This signal sends the submitted text to the LLM with a prompt asking it to estimate the probability that the text was AI-generated. The model evaluates things like generic hedging language ("it is important to note"), overly balanced paragraph structure, lack of personal voice, and uniform sentence rhythm. It returns a score between 0.0 (confident this is human) and 1.0 (confident this is AI).

**What it captures well:** Semantic coherence, the overall "feel" of the writing, patterns that are hard to reduce to simple statistics.

**What it misses:** The LLM is not deterministic. The same text can get slightly different scores across runs. It also tends to flag formal human writing (academic papers, legal briefs) as AI-like because the style overlap is significant. There is also an inherent bias risk when one LLM is judging the output of another.

### Signal 2: Stylometric Heuristics (Pure Python)

This signal computes three structural metrics:

- **Sentence length variance:** Measures the coefficient of variation in sentence lengths. Human writers naturally vary between short punchy sentences and longer ones. AI text tends to cluster around a comfortable middle.
- **Type-token ratio (TTR):** Unique words divided by total words. Higher TTR means more diverse vocabulary, which is more typical of human writing. AI text tends to reuse the same terms more often.
- **Punctuation density:** Ratio of punctuation characters to total characters. Human writing, especially casual or creative writing, uses more varied and frequent punctuation. AI text is punctuation-conservative.

Each metric produces a sub-score between 0.0 and 1.0, and the three are averaged into a single heuristic score.

**What it captures well:** Surface-level statistical patterns that are cheap to compute and genuinely different between most human and AI text.

**What it misses:** Formal human writing (research papers, policy documents) naturally has low sentence variance and conservative punctuation, so it gets flagged as AI-like. Very short texts (under 50 words) do not give the metrics enough data. Poetry with intentional repetition will trip the TTR metric.

## Confidence Scoring

The two signal scores are combined using a weighted average:

```
combined_score = (0.6 * llm_score) + (0.4 * heuristic_score)
```

The LLM signal gets more weight because it captures meaning, not just surface statistics. The heuristic signal serves as a structural cross-check. When both agree, confidence is strong. When they disagree, the combined score naturally falls into the uncertain range.

### Thresholds

| Combined Score | Classification | Label Tier |
|---|---|---|
| 0.75 to 1.0 | Likely AI | High-confidence AI label |
| 0.40 to 0.74 | Uncertain | Inconclusive label |
| 0.0 to 0.39 | Likely Human | High-confidence human label |

The uncertain band is intentionally wide. The system would rather say "we're not sure" than wrongly accuse a human writer.

### Validation: Two Example Submissions with Different Scores

**High-confidence human (score: 0.2533):**

Input: casual, informal restaurant review with slang, sentence fragments, capitalized emphasis ("WAY too much sodium"), and natural voice.

```json
{
    "attribution": "likely_human",
    "confidence": 0.2533,
    "llm_score": 0.2,
    "heuristic_score": 0.3333,
    "label": "Our analysis indicates this content is likely human-written (confidence: 75%). No action is needed."
}
```

Both signals agreed this was human. The LLM picked up on the informal tone and genuine personal experience. The heuristics detected high sentence length variation and casual punctuation patterns.

**Uncertain, leaning AI (score: 0.6839):**

Input: formal academic paragraph about monetary policy with uniform sentence structure and technical vocabulary.

```json
{
    "attribution": "uncertain",
    "confidence": 0.6839,
    "llm_score": 0.8,
    "heuristic_score": 0.5098,
    "label": "Our analysis was inconclusive for this content (confidence: 68%). The result may reflect either AI-assisted or human-written text. If you believe this result is wrong, you can submit an appeal."
}
```

The LLM flagged this strongly (0.8) because it reads like typical AI output. But the heuristics were more moderate (0.51) because the text did have some structural variation. The combined score landed in the uncertain band, which is actually the correct result for formal human writing that resembles AI output. The system did not commit to calling it AI, and it offered the appeal path.

## Transparency Label

Three label variants, designed for non-technical readers:

| Classification | Label Text |
|---|---|
| High-confidence AI (score >= 0.75) | "Our analysis indicates this content is likely AI-generated (confidence: {X}%). If you believe this is incorrect, you can submit an appeal." |
| Uncertain (score 0.40 to 0.74) | "Our analysis was inconclusive for this content (confidence: {X}%). The result may reflect either AI-assisted or human-written text. If you believe this result is wrong, you can submit an appeal." |
| High-confidence Human (score < 0.40) | "Our analysis indicates this content is likely human-written (confidence: {X}%). No action is needed." |

Design choices:
- Every label includes the word "likely" because the system never claims certainty.
- The confidence percentage always reflects confidence in the stated classification. For "likely human," the percentage is (1 minus the raw score), so a low raw score of 0.25 displays as "confidence: 75%."
- Appeal language appears in the AI and uncertain labels but not in the human label, since a human classification is unlikely to be contested.
- No jargon. No mention of "classifiers," "signals," or "scores." A reader sees a plain sentence and a percentage.

## Appeals Workflow

Creators can contest any classification by sending a `POST /appeal` request with their `content_id` and a written explanation of why they believe the result is wrong.

When an appeal is received, the system:
1. Looks up the original classification
2. Updates the content status from "classified" to "under_review"
3. Logs the appeal as a separate entry in the audit log, preserving the original scores alongside the creator's reasoning
4. Returns a confirmation

Example appeal response:
```json
{
    "content_id": "55a71278-74b6-478f-9000-8f3405618e89",
    "message": "Appeal received. Content status updated to under review.",
    "status": "under_review"
}
```

The audit log entry for the appeal includes the original attribution, original confidence, both original signal scores, and the creator's reasoning, so a human reviewer has everything they need in one place. Automated re-classification is not implemented.

## Rate Limiting

The submission endpoint is rate-limited to **10 requests per minute and 100 requests per day** per IP address.

**Reasoning:** On a creative writing platform, a single creator might submit a handful of pieces in a sitting, but not dozens per minute. Ten per minute is generous for legitimate use (submitting a few drafts back to back) while blocking a script that tries to flood the system or probe the classifier for weaknesses. The daily cap of 100 accounts for a prolific creator while still preventing sustained abuse. The appeal endpoint has a separate, tighter limit of 5 per minute since there is no legitimate reason to file appeals that rapidly.

## Known Limitations

**Formal human writing gets flagged as AI-like.** This is the most significant limitation. Academic writing, legal briefs, and policy documents naturally have the same characteristics the system associates with AI: uniform sentence length, conservative punctuation, formal vocabulary, and balanced paragraph structure. Both signals struggle with this overlap. The LLM signal tends to rate formal text at 0.7 to 0.8 because the style genuinely resembles LLM output, and the heuristic signal does not pull the score down enough to compensate. In testing, a human-written academic paragraph about monetary policy scored 0.6839, landing in the uncertain band rather than the human band. The wide uncertain range helps here (it prevented a false positive), but a very polished formal essay could still cross into the 0.75 threshold and get a high-confidence AI label. The appeals workflow is the safety net for these cases.

**Short texts are unreliable.** Anything under about 50 words does not give the stylometric heuristics enough data. The sentence length variance of 2 sentences is basically noise. For short submissions, the system falls back almost entirely on the LLM signal, which makes the confidence score less trustworthy. These usually land in the uncertain band, which is the honest answer, but it also means short-form writers get a less useful result.

## Spec Reflection

**How the spec helped:** Writing out the three label variants in planning.md before building the label generation function saved real time. When I got to implementation, the function was just a direct translation of the spec. There was no design decision left to make in the code. The same was true for the confidence thresholds. Having 0.75 / 0.40 / 0.39 written down meant I could test whether inputs landed in the right tier without second-guessing the ranges while debugging.

**Where implementation diverged:** The spec originally described the confidence percentage as just the raw combined score. During testing, I realized that for "likely human" results, showing a low percentage (like 25%) felt confusing. A reader sees "likely human-written (confidence: 25%)" and thinks the system is not confident, when actually the low score means high confidence in the human classification. So I flipped the display for human labels to show (1 minus the score) as the percentage, making "confidence: 75%" match the reader's intuition. The underlying score did not change, just how it is presented in the label text.

## Setup and Running

1. Clone the repo
2. Create a virtual environment: `python -m venv .venv`
3. Activate it: `source .venv/bin/activate` (Mac/Linux) or `source .venv/Scripts/activate` (Git Bash on Windows)
4. Install dependencies: `pip install -r requirements.txt`
5. Create a `.env` file with your Groq API key: `GROQ_API_KEY=your_key_here`
6. Run: `python app.py`
7. Server starts at `http://localhost:5000`
